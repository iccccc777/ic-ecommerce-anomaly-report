# 面试故事：电商经营异动归因与智能日报系统

## 0. 一分钟版本

我做了一个电商经营异动归因与智能日报项目。数据集是淘宝 9 天用户行为数据，约 1 亿行。为了保留用户行为连续性，我没有按行抽样，而是按 `user_id` 稳定哈希保留约 2% 用户，得到 19,476 个用户和 196.7 万行行为。

我先用 SQL 建了行为事实表和用户、商品、类目维表，再统一定义 DAU、PV、收藏、加购、购买和购买/浏览比。异常检测没有只看环比，而是组合 3 日移动平均、同星期基线和留一法 Z-Score。结果发现 12 月 2 日和 3 日连续强异动，DAU 接近 1.91 万，较上周同星期日期分别增长 38.5% 和 35.0%。

归因后发现，购买增量主要集中在 16-21 时；DAU 净增 4,595 主要来自新增活跃用户，但数据不能证明他们是新注册用户。之后我把聚合结果交给 DeepSeek 生成日报初稿，再人工校准掉“新用户涌入”“渠道拉新”等过度结论。这个项目的价值不是简单调用模型，而是形成“数据口径、异常定位、归因、AI 提效、人工验收、业务建议”的闭环。

## 1. 业务问题

### 背景

电商平台每天都有 DAU、PV、购买等波动。业务真正关心的不是“昨天涨了多少”，而是：

1. 这次波动是不是正常周期？
2. 增长或下滑集中在什么时间、类目和用户群体？
3. 能不能给出运营可以执行的动作？
4. 如果使用大模型，如何提效又不让模型编造结论？

### 我的分析问题

我把项目目标定义为：

> 在 2017-11-25 到 2017-12-03 的窗口内，识别经营异常日，定位主要变化维度，并产出经过数据校验的中文经营日报。

## 2. 指标口径

原始数据字段是：

```text
user_id, item_id, category_id, behavior_type, timestamps
```

行为包括 `pv`、`fav`、`cart`、`buy`。数据没有价格、订单金额和支付金额。

因此我明确采用以下口径：

| 指标 | 定义 |
|---|---|
| DAU | 当天有任意行为的去重用户数 |
| PV | 当天 `pv` 事件数 |
| 收藏 | 当天 `fav` 事件数 |
| 加购 | 当天 `cart` 事件数 |
| 购买 | 当天 `buy` 事件数；作为购买量代理指标 |
| 购买/浏览比 | `buy / pv` |
| 人均购买次数 | `buy / DAU` |

我没有计算 GMV 和客单价，因为数据没有金额；也没有把 9 天窗口用户数称为 MAU。`funnel.csv` 也只称为窗口期用户重叠率，因为同一个用户的行为不保证按浏览、加购、购买的顺序发生。

面试时可以强调：

> 指标口径比指标数量重要。相同名称如果口径不同，业务结论可能完全相反。

## 3. 数据加工

### 数据版本

| 项目 | 数值 |
|---|---:|
| 原始行数 | 100,150,807 |
| 原始文件大小 | 3,672,347,465 字节 |
| 分析窗口 | 2017-11-25 至 2017-12-03 |
| 抽样方式 | 按 `user_id` 稳定哈希保留约 2% 用户 |
| 抽样用户 | 19,476 |
| 抽样行为 | 1,966,733 行 |
| 窗口内清洗后 | 1,965,596 行 |

### 为什么按用户抽样

最初行级抽样会让用户行为序列断裂，用户指标会产生假象。改成用户级抽样后，同一用户的所有行为一起保留，DAU、留存和“窗口内首次出现”才有一致口径。

### SQL 数仓

我建立了：

- `behavior`：用户、商品、类目、行为、时间戳的行为事实表。
- `behavior_clean`：限定到 2017-11-25 至 2017-12-03 的清洗视图。
- `dim_user`：用户行为次数、活跃天数、首次和最后时间。
- `dim_item`：商品行为次数和用户数。
- `dim_category`：类目行为次数和用户数。

时间统一使用：

```sql
date(timestamps, 'unixepoch', '+8 hours')
```

## 4. 分析方法

### 异常检测

只有 9 天数据，单一 Z-Score 或环比都不稳。我用了三层信息：

1. 3 日移动平均：看短期趋势。
2. 7 天前同星期基线：控制周末效应。
3. 留一法 Z-Score：判断当天时，不让当天参与均值和标准差计算。

DAU、PV、buy 分别计算。绝对 Z 值大于 1.5 标记为异动，大于 2.0 标记为 strong。

最终结果：

- 12-02：DAU 19,118，较上周六 +38.50%，DAU Z 值 2.49，strong。
- 12-03：DAU 19,059，较上周日 +34.97%，DAU Z 值 2.42，buy Z 值 2.53，strong。

### 异动归因

我把 12-02 和 12-01 对比，分别拆解三个维度：

1. 类目：看哪个类目贡献了购买增量。
2. 时段：看购买增量集中在几个小时的窗口。
3. 用户：把 DAU 变化拆成两日都活跃、新增活跃和流失。

结果：

- 总购买增量 +963。
- 16-21 时合计 +548，贡献 56.91%。
- 21 时 +127、17 时 +123、16 时 +105。
- 类目 Top 5 只贡献约 9.45%，头部类目各增加 21 次，增长较分散。
- 两日都活跃 14,258 人；新增活跃 4,860 人；流失 265 人；净增 4,595 人。

### 业务解释

我最终给业务三条建议：

1. 优先审视 16-21 时的排期、触达和资源位。
2. 对增量头部类目做供给、价格和活动交叉验证，不凭单个 21 次购买增量下结论。
3. 对新增活跃用户继续分析行为路径和后续回流，再决定是否做定向触达。

## 5. AI 提效

### 我的做法

我没有让模型直接访问数据库，也没有让模型自由发挥。流程是：

```text
SQL/Python 先产出结构化结果
-> 组装受控提示词
-> DeepSeek 生成日报初稿
-> 记录提示词和返回内容
-> 人工逐项校准
-> 看板只展示校准版
```

调用模型为 `deepseek-chat`，调用记录保存在 `outputs/ai_call_log.json`。

### 人工校准发现了什么

AI 初稿把“新增活跃用户”扩写成“新用户涌入”，并进一步推测为“外部渠道拉新”。这是数据无法证明的。

我做了三类修正：

1. 把“新用户/拉新”改成“新增活跃用户”。
2. 给类目结论加上“单类目增量小、需要交叉验证”的限制。
3. 所有关键数字回到 `outputs/` CSV 逐项核对。

面试表达：

> 大模型在这个项目里不是结论生成器，而是结构化结果的表达加速器。它负责提高日报初稿效率，数据口径、因果边界和最终判断由人和可验证数据负责。

12-02 和 12-03 是连续强异动日，且超过同星期基线。增长同时体现在 DAU 和购买规模，购买效率没有明显被稀释。购买增量主要集中在 16-21 时，DAU 净增主要由新增活跃用户贡献，但来源未知。

## 7. 常见追问

### Q1：为什么不用全量数据？

全量原始文件约 3.42 GB，本项目主要验证完整分析链路。用户级 2% 抽样保留了单个用户的行为连续性，适合观察趋势和归因。缺点是小类目波动大，因此不能把抽样值直接外推全量，也没有依据小类目做单点结论。

### Q2：为什么异常检测用移动平均还要用 Z-Score？

移动平均表达短期偏离，Z-Score表达相对历史波动幅度的异常程度，同星期基线用于控制周末效应。三种方法组合比单一日环比更稳。

### Q3：为什么不能直接说新增活跃用户就是新用户？

数据没有注册时间和历史全量活跃日期。我只能知道这些用户 12-01 未活跃、12-02 活跃，不能判断他们在窗口之前是否已经注册，也不能判断流量渠道。

### Q4：为什么不能写购买漏斗转化率？

当前 `funnel.csv` 是窗口内各行为去重用户数的重叠关系，没有约束先后顺序，因此不是严格漏斗。严格漏斗要按每个用户行为时间序列求首次浏览、首次加购/收藏、首次购买。

### Q5：AI 在这个项目里到底有什么价值？

它把结构化聚合结果快速转成中文日报初稿，减少格式整理时间；同时调用日志保留模型、提示词和结果，便于审核。价值在于提效和可追踪，不在于替代数据分析判断。

### Q6：如果继续做，你最先补什么？

首选补价格和订单金额，因为只有补齐金额才能从流量和购买行为走到 GMV、客单价和收入。第二个补活动和渠道数据，才能进一步验证本次增长是否由活动或投放驱动。

### Q7：数据库迁移这块你具体做了什么？

我没有只把表名和 SQL 换个写法。我用 MySQL 8 真实迁移了 1,966,733 行行为记录，使用 `LOAD DATA LOCAL INFILE` 批量导入，导入完成后再创建复合索引。日期口径从 SQLite 的 `unixepoch` 改成 `FROM_UNIXTIME` 加北京时间转换；比率列显式转换为 `DECIMAL(20, 10)`，避免 MySQL 整数除法默认只有 4 位小数。

迁移后，我用脚本把 MySQL 的日指标、异常检测、窗口期重叠、留存和三个归因结果与 SQLite 基线逐项比较，7 个文件全部一致。PostgreSQL 也提供了等价方言和静态检查，但当前机器没有 PostgreSQL 服务，所以我没有写成“真实跑通 PostgreSQL”。
