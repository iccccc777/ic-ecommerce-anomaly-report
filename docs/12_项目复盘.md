# 项目复盘：电商经营异动归因与智能日报系统

## 1. 项目目标

项目基于淘宝用户行为数据，打通一条可复现的数据分析闭环：

```text
数据抽样与清洗 -> SQLite 数仓 -> 指标口径 -> 异常检测
-> 异动归因 -> LLM 日报 -> 人工校准 -> 看板与业务建议
```

重点不是展示“处理了多少行数据”，而是回答三个业务问题：

1. 2017-12-02 和 12-03 的活跃与购买增长是否只是周末波动？
2. 增长集中在哪些时段、类目和用户变化上？
3. 大模型能否提高日报初稿效率，同时避免把未经证实的内容写成结论？

## 2. 遇到的问题、怎么解决

### 问题 1：行级抽样破坏用户行为连续性

早期若按行随机抽样，同一用户的行为会被打散，导致新用户、留存和 DAU 口径失真，甚至制造出并不存在的“大量新用户”。

解决方案：

- 改为按 `user_id` 做稳定哈希，保留约 2% 用户的全部行为记录。
- 同一份原始数据下，抽样结果可重复。
- 最终得到 19,476 个用户、1,966,733 行行为记录。

数据证据：

| 项目 | 数值 | 来源 |
|---|---:|---|
| 原始数据 | 100,150,807 行 | `docs/04_数据版本与抽样说明.md` |
| 用户级抽样行为 | 1,966,733 行 | `data/ecommerce.db` |
| 窗口内清洗后行为 | 1,965,596 行 | `behavior_clean` |
| 被窗口规则排除的脏时间戳 | 1,137 行 | `docs/05_指标口径.md` |
| 抽样用户数 | 19,476 | `outputs/funnel.csv` |

### 问题 2：指标看起来很多，但部分口径没有数据基础

原始数据只有用户、商品、类目、行为类型和时间戳，没有价格、订单金额和支付金额。

解决方案：

- 不伪造 GMV、客单价。
- 以 `buy` 行为次数作为购买量代理指标。
- `buy / pv` 定义为购买行为/浏览行为，不表述为“支付转化率”。
- 只有 9 天数据，因此不把窗口活跃用户数包装成 MAU。

数据证据：

- 12-02：PV 241,527，buy 5,080，`buy_to_pv = 2.1033%`。
- 12-03：PV 242,349，buy 5,258，`buy_to_pv = 2.1696%`。
- 来源：`outputs/daily_metrics.csv`、`docs/05_指标口径.md`。

### 问题 3：窗口期用户重叠率容易被误读成严格漏斗

`funnel.csv` 只统计 9 天内发生过浏览、加购、收藏、购买的去重用户，没有强制行为先后顺序，因此不是严格漏斗。

解决方案：

- 报告中统一称为“窗口期用户重叠率”。
- 不写“购买漏斗转化率 68.49%”。
- 明确严格漏斗需要按用户行为时间序列计算首次浏览、首次加购/收藏、首次购买。

数据证据：

| 行为 | 用户数 | 相对浏览用户 |
|---|---:|---:|
| 浏览 `pv` | 19,410 | 100.00% |
| 加购 `cart` | 14,545 | 74.94% |
| 收藏 `fav` | 7,700 | 39.67% |
| 购买 `buy` | 13,293 | 68.49% |

来源：`outputs/funnel.csv`。

### 问题 4：只有 9 天数据，单一阈值容易把周末效应误判为异动

直接看日指标，12-02 和 12-03 的周末增长很显眼，但不能只凭“比前一天高”判断异常。

解决方案：

- 使用前 3 日移动平均观察短期偏离，不把当天纳入自身基线。
- 使用 7 天前同星期基线，减少周末效应干扰。
- 使用留一法 Z-Score，计算某天时不把当天纳入均值和标准差。
- DAU、PV、buy 分别判断，任一指标绝对 Z 值大于 1.5 为 mild，大于 2.0 为 strong。

数据证据：

| 日期 | DAU | 较上周同星期 | DAU Z | PV Z | buy Z | 级别 |
|---|---:|---:|---:|---:|---:|---|
| 2017-12-02 | 19,118 | +38.50% | 2.49 | 2.33 | 1.74 | strong |
| 2017-12-03 | 19,059 | +34.97% | 2.42 | 2.40 | 2.53 | strong |

来源：`outputs/anomaly_detection.csv`。

### 问题 4.1：自动测试原先只覆盖本机

数据库 SQL、时区和异常基线如果只在本地手工验证，修改后很容易回归。

解决方案：

- 为 MySQL 会话时区和 trailing baseline 增加回归测试。
- 增加 PostgreSQL 16 实例级集成测试。
- 增加 GitHub Actions，自动启动 MySQL 8 和 PostgreSQL 16。
- 每次 push 和 pull request 都运行完整测试套件。

数据证据：

- 工作流：`.github/workflows/tests.yml`。
- 测试目录：`tests/`。
- 本地数据库测试通过；PostgreSQL 测试由 GitHub Actions 执行。

### 问题 5：类目购买增量小，单类目容易产生伪结论

12-01 到 12-02 的总购买增量为 +963，但分散在大量类目中。头部类目只增加 21 次，继续拆类目后统计噪声明显增大。

解决方案：

- 同时查看类目、时段和用户变化，避免只凭一个维度下结论。
- 类目结论保留为“分散、无单一爆款主导”的方向性判断。
- 时段归因结合小时级增量，业务动作更容易落地。
- 用户变化只写“新增活跃”和“流失活跃”，不推断新注册或渠道来源。

数据证据：

- 12-02 较 12-01 总购买增量：+963。
- 16-21 时购买增量合计：+548，占总增量 56.91%。
- 21 时 +127、17 时 +123、16 时 +105、19 时 +97、20 时 +74。
- 类目 Top 5 合计贡献约 9.45%，最大两个类目各贡献 2.18%，各增加 21 次。
- DAU 净增 +4,595：两日都活跃 14,258，新增活跃 4,860，流失 265。

来源：`outputs/attribution_hour.csv`、`outputs/attribution_category.csv`、`outputs/attribution_user_segment.csv`。

### 问题 6：AI 会主动补出不存在的业务解释

DeepSeek 初稿把“新增活跃用户”扩写为“新用户涌入”，并进一步推测为“外部渠道拉新”。这些说法超出了数据能证明的范围。

解决方案：

- 在提示词中明确“新增活跃不是新用户贡献”。
- 保留模型、提示词、返回内容和调用时间到 `outputs/ai_call_log.json`。
- 人工校准所有数字、业务判断和行动建议。
- 最终看板读取人工校准版，不让未审核的 AI 初稿直接对外表达。

数据证据：

- 调用记录：`outputs/ai_call_log.json`。
- 使用模型：`deepseek-chat`。
- 初稿：`outputs/daily_report.md`。
- 人工校准版：`outputs/daily_report_calibrated.md`。

### 问题 7：数据不能提交 GitHub，但报告需要保留可复现证据

原始 CSV 约 3.42 GB，抽样 CSV 约 74 MB，SQLite 约 180 MB，不适合进入普通 Git 仓库；`.env` 还包含 API Key。

解决方案：

- `.gitignore` 排除 `.env`、`.venv`、原始/抽样 CSV、数据库、缓存和运行日志。
- 保留代码、SQL、数据字典、口径、报告、关键 CSV 和异常图。
- README 写明数据来源、版本、SHA256 和重建命令。

### 问题 8：SQLite 便于本地复现，但不够贴近岗位数据库环境

SQLite 适合单文件开发，但实际数据岗位更常要求 MySQL/PostgreSQL、复合索引、批量导入和方言改写。

解决方案：

- 新增完整 MySQL 8 方言，将 1,966,733 行行为记录迁移到 MySQL。
- 使用 `LOAD DATA LOCAL INFILE` 批量导入，并在导入后创建二级索引。
- 修正 MySQL 整数除法的精度问题，所有比率显式转换为 `DECIMAL(20, 10)`。
- 用 `(behavior_type, user_id)`、`(category_id, user_id)` 等复合索引优化去重聚合。
- 将 MySQL 输出与原 SQLite 的 7 个结果文件逐项比较。
- 另外提供 PostgreSQL 方言和静态检查，但不声称做过未执行的实例验证。

数据证据：

- MySQL 行为行数：1,966,733，与 SQLite 一致。
- 用户数：19,476；商品维表：628,715 行；类目维表：6,559 行。
- `daily_metrics`、`anomaly_detection`、`funnel`、`retention` 和 3 个归因结果全部通过一致性校验。
- 迁移说明：`docs/14_数据库迁移.md`。
- 结果目录：`outputs/mysql/`。

## 3. 业务结论

### 结论 1：12-02 和 12-03 是连续强异动日，不能仅解释为周末效应

两天 DAU 都接近 1.91 万，显著高于此前 1.38 万到 1.45 万的日常区间。与 7 天前同星期日期相比，DAU 分别增长 38.50% 和 34.97%，购买行为分别增长 31.20% 和 29.09%。

### 结论 2：流量和购买同步上升，购买效率没有明显被稀释

12-02 的 `buy_to_pv` 为 2.1033%，12-03 为 2.1696%，与 12-01 的 2.1503% 接近。可以判断增长同时体现在活跃和购买规模上，但不能据此判断增长来自某个具体活动。

### 结论 3：购买增量主要集中在 16-21 时

16-21 时贡献了 56.91% 的购买增量，其中晚间 21 时最高。对运营侧的可执行含义是：排期、触达和资源位优先覆盖晚间高峰，再用正式实验验证效果。

### 结论 4：DAU 增长主要由新增活跃用户驱动，但来源未知

12-02 的 DAU 净增为 4,595。两日都活跃的用户有 14,258 人，12-01 未活跃而 12-02 活跃的用户有 4,860 人，12-02 流失 265 人。

这里只能说明“新增活跃用户”推动了净增量。现有数据没有注册时间、渠道和投放信息，不能写成新注册用户、拉新成功或渠道 ROI。

### 结论 5：类目增长分散，不具备单独锁定爆款的证据

Top 5 类目只解释约 9.45% 的总购买增量，头部类目各增加 21 次购买行为。更合理的动作是先做供给与活动交叉验证，而不是直接宣布某个类目是增长来源。

### 结论 6：留存数字可用性有限

Day 1 留存率范围约为 59.49% 到 97.56%。由于 9 天窗口左截断，“首日”只是窗口内首次出现日，不是真实注册日，因此不能把这些数字解释为真实获客留存。

## 5. 局限与下一步

### 当前局限

- 用户级抽样约 2%，指标不能直接外推全量业务。
- 只有 9 天数据，无法计算真实 30 天 MAU，留存受左截断影响。
- 缺少价格和订单金额，无法计算 GMV、客单价、收入和 ROI。
- 缺少活动、渠道、商品价格、库存和竞品信息，无法做因果归因。
- 类目层购买增量稀疏，细分维度存在统计噪声。

### 下一步

1. 补充价格表和订单表，建立收入指标闭环。
2. 接入渠道、活动和曝光信息，区分自然流量、投放和活动影响。
3. 对 16-21 时运营触达做真实 A/B 实验，以 `buy_to_pv`、购买用户数和后续留存为主要指标。
4. 按首次浏览到首次购买的顺序重做严格漏斗。
5. 使用更长窗口计算 MAU、复购和高价值用户分层。
